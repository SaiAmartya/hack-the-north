# Normal-mode input timing — September 20, 2026

## Evidence and scope

Sai requested normal-mode timing repairs after suspecting BLE latency cuts the gesture snippet. The existing Simple motion work remains opt-in and separate. This pass changes software recognition/pairing, without firmware or transport protocol changes.

Both supplied browser traces have complete streaming packets: 550/550 samples in 08:22 and 6437/6437 streaming/validation samples in 08:46 (14 earlier notifications occurred during handshake). Neither has sequence loss, rejected streaming samples, device drops or discontinuity flags. Acquisition intervals remain 18–23 ms despite notification batching up to 90.5 ms. The maximum accepted age bound is 132 ms. The data does not support blaming signal loss or increasing stale-packet allowances.

Two actual timing defects were identified:

- Gesture onset retained only the previous sample (~20 ms). A subthreshold upward launch can be lost before a stronger brake crosses onset. Retaining 120 ms of feature context recovers launch/brake order. Onset timing, duration floors and personal DTW exclude this added context, preventing quiet padding from creating a gesture.
- Every five seconds, a clock probe replaces the capture-to-browser offset. The longer trace has 26 changes of −10.25 to +23.75 ms; regular acquisition can appear as isolated 10.1–43.75 ms intervals. A concrete 63 ms candidate appeared to last 55.3 ms. Gesture shape and jerk now use acquisition-clock deltas; each active movement keeps one browser-clock anchor for speech alignment. Correcting duration alone did not recover that particular recorded candidate, which also failed other gates.

Clock discontinuities between movements still reset rest tracking. Removing that existing reset exposed a false jab in Protego trial 8: a small resting-baseline difference moved a return just below the old 18° lowering threshold. The narrower repair preserves recorded negatives while preventing clock corrections from shortening or breaking an active movement. Actual capture gaps, age checks, flags and generation resets still invalidate discontinuous evidence.

## Pairing changes through v5

The cancellation policy in this historical section is superseded by the speech-first repair below.

Normal mode retains up to eight recent typed gestures, selects a temporally compatible matching class using captured intervals, and consumes the attempt once. An unrelated or wrong candidate no longer immediately discards a good word. Jab/raise requirements remain.

The initial v4 pass increased the normal-mode gap from 350 to 900 ms. The subsequent v5 pass allows **two seconds in either direction** and a **six-second total span**, with a seven-second maximum pending lifetime. These are capture-time bounds, not a delay before casting: a complete matching pair submits immediately. A mismatch fizzle waits for the opportunity to close. The one-second speech-result deadline, one local inference job, sample-age/gap guards, generation resets and duplicate consumption remain. Simple motion keeps its prior 350 ms / two-second limits.

A newly confirmed word can replace an older unmatched word. A newer sound holds overlapping movement until it resolves. Only a validated, timely, silence-ended `no-speech` or `not-an-incantation` result restores pairing with the retained word. Ambiguous cancellation, low confidence, timeout and cutoff clear the attempt rather than assign a second command's movement to the first word. Only one confirmed word and one active recognition are retained, with bounded motion history. The speech client additionally remembers one completed natural-inference interval so a delayed onset captured while inference was busy remains suppressed after the result arrives.

## V5 speech-first and multiplayer follow-up

The prior 900 ms window left unequal time to react to feedback: gesture evidence in the supplied traces arrived about 192 ms after movement (184–209 ms for raises), while accepted speech arrived 509–542 ms after voice end. Both still used captured intervals correctly, but speech-first players had less time remaining. The new two-second bound applies symmetrically and does not add callback latency to captured movement duration.

A movement that finished before a newer sound started could be held by that sound merely because classification arrived later. Capture-time ownership now lets that completed movement pair with the earlier word while retaining the newer utterance for its own next movement. A movement overlapping a newer utterance still waits for its result; a newly confirmed spell replaces an unmatched older word. Final review rejected unconditional fallback after cancellation: forced-cutoff continuation, timeout, interruption, low-confidence and unknown results clear both words and buffered movement. Only explicit, valid, timely, silence-ended non-spell results preserve the earlier word. This prevents an interrupted second command from firing the first spell with the second command's movement.

An audio-clock lifecycle reproduction found that a visible AudioContext suspension could pause its frame clock while browser time continued, leaving future contiguous frames incorrectly timestamped. The capture adapter now retires a stopped/interrupted audio context and queued callbacks; a fresh microphone session gets a fresh clock origin. It does not restamp delayed audio or claim that this interruption occurred in Sai's last test.

Accepted-cast telemetry now includes both capture intervals, speech final time, order and measured gap, under normal profile `quick-play-jab-raise-v5`. This makes later separation failures measurable without deriving the interval from UI feedback.

Multiplayer presentation also had a separate delay failure: authoritative HP could update while the own-cast animation event was discarded by the 300 ms event-age guard. The controller now correlates a pending cast with its referee acknowledgement for up to two seconds and presents acceptance exactly once. Bounded pending/action histories, room/round/input generations and lifecycle checks retire stale acknowledgements; no optimistic damage or retries were added.

## Speech-first cancellation repair (after a5c575d)

Fresh physical testing still reports speech-then-motion misses. No post-release telemetry was supplied, so this pass identifies reproducible source failures without attributing every physical miss to them. Two order-dependent cancellation paths survived v5: a later microphone onset could block and then erase an already confirmed word, and a brief `breaksGesture` sample reset independent speech as well as motion. Motion-first could consume its pair before either event occurred. The prior browser helper also waited for the speech result before starting its speech-first movement; it did not test immediately moving while transcription was still pending.

Normal fusion now arms the first confirmed word for a gesture beginning within the existing two-second post-speech interval. Later sounds beginning during that interval cannot block, replace or cancel it. After it casts, the next fresh utterance is admitted immediately; if no cast occurs, a new utterance after the two-second interval replaces it. This deliberately makes one spoken command own one movement: to change an uncast spell, wait two seconds after finishing the first word. Delayed gesture results remain bounded by the existing six-second span/seven-second retention, with no relaxed classification, stale-packet or speech-final deadline. Simple motion keeps its existing policy.

A brief wand discontinuity now clears only motion candidates, preserving active or confirmed laptop speech and consumed IDs. The recognizer still discards a burst interrupted by missing samples, so a whole clean gesture is required after the gap. Disconnect, input generation, page visibility and room changes still reset the full attempt.

## Microphone stability follow-up

The speech-first repair was published to main as `bad981b` before this follow-up. The user's next report was frequent microphone disconnects requiring Enable microphone during battle; no new physical telemetry accompanies this report.

Source audit reproduced four avoidable shutdown paths: generic `mediaDevices.devicechange` stopped a healthy active mic; any AudioContext suspension required a manual restart; empty worklet input (zero channels) was rejected as a permanent non-mono format error before its discontinuity could be recovered; and repeated helper errors closed working microphone capture. These are concrete control-flow failures, not attribution of every observed physical disconnect. Web Audio explicitly permits empty worklet inputs when no source is actively processing ([W3C Web Audio specification](https://www.w3.org/TR/webaudio/)); an interrupted AudioContext is distinct from permanently ended capture ([MDN context state](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state)).

The platform now ignores unrelated device inventory changes, coalesces each missing-input outage into one immediate reset, recalibrates resumed PCM, and monitors ongoing frame delivery. A recoverable audio-clock/worklet/PCM-outage failure gets a fresh capture session and clock after 250 ms, limited to two automatic restarts in 30 seconds. Explicit stop, hidden page, track end, permission/setup failure and exhausted retries do not loop. Fusion is cleared at the capture reset so old speech cannot cast after recovery. Helper 5xx/network errors discard the utterance while preserving the mic; the third failure shows an issue until the helper responds successfully. Stale replies cannot mutate a replacement session.

The first browser recovery run found another real integration failure: capture restarted correctly, but the referee aborted the active round on its first `healthy:false` heartbeat during recalibration. The frontend now grants up to five seconds of heartbeat grace only during known automatic capture recovery. Actual Ready/cast gating remains unavailable; hidden pages, lost wands, renderer failures and expired recovery still report unhealthy. No referee protocol or hosted code changes were needed.
